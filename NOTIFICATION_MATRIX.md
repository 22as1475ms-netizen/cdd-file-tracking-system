# Notification Matrix

This document lists the recommended notification events for CDD-File-Tracking-System, who should receive them, and why they are useful.

The goal is not to notify every action. The goal is to notify the right user when something needs attention, confirmation, or awareness.

This file also separates `notifications` from `announcements`:

- `Notifications`
  Event-driven alerts tied to workflow actions or account changes.
- `Announcements`
  Intentional broadcast messages created by Super Admin for a wider audience.

**Principles**

- Notify the person who needs to act.
- Notify the person who needs visibility into a completed or failed workflow step.
- Avoid noisy notifications for low-value events like page visits or simple screen opens.
- Prefer short, linkable notifications that take the user directly to the related file or account.

**Recommended Notification Categories**

- `Account`
- `Routing`
- `Review`
- `Section`
- `System`

**Notifications vs Announcements**

Notifications should be generated by actual system events.

Examples:

- a file was routed to you
- a route was completed
- a document was approved

Announcements should be manually created by Super Admin and broadcast to a chosen audience.

Examples:

- office event reminder
- workflow deadline
- maintenance advisory
- section-wide announcement

**Account Notifications**

1. New account created

- Trigger:
  Super Admin creates a new account.
- Recipients:
  - the Section Admin if the new account is a `SECTION_STAFF` account under their section
- Why:
  The Section Admin should know that a new staff member is now part of their section.

2. Password reset by admin

- Trigger:
  An admin resets another user’s password.
- Recipients:
  - none as an in-app notification if the user cannot currently access the system
- Why:
  This is better handled outside the in-app notification feed, because a locked-out or inactive user may not be able to log in and read it.

3. Account enabled or disabled

- Trigger:
  A user account is re-enabled or disabled.
- Recipients:
  - optionally Super Admin for audit visibility
- Why:
  This is important account-access information, but not useful as an in-app notification for a disabled user who cannot enter the system.

**Routing Notifications**

1. A routed file was shared with you

- Trigger:
  A file is routed/shared to a user.
- Recipients:
  - the receiving user
- Why:
  This is the most important action-driven notification in the system.

2. Section Admin routed a file to Section Staff

- Trigger:
  Section Admin routes a file to one of their section staff.
- Recipients:
  - the receiving Section Staff
  - optionally the Section Admin as confirmation
- Why:
  The staff member needs to act on it.

3. Route completed

- Trigger:
  The final routed holder marks the route complete.
- Recipients:
  - the Section Admin involved in that routed chain
  - Super Admin/Admin if they need global visibility
  - optionally earlier routed participants in the same route chain
- Why:
  Completion is a major lifecycle event.

**Review Notifications**

1. Review assignment sent

- Trigger:
  A document is assigned for review.
- Recipients:
  - the assigned reviewer
- Why:
  Reviewer needs to know work is waiting.

2. Document approved

- Trigger:
  Review flow marks the document approved.
- Recipients:
  - the owner or responsible admin
  - optionally routed stakeholders
- Why:
  Important final review outcome.

3. Document rejected

- Trigger:
  Review flow marks the document rejected.
- Recipients:
  - the owner or responsible admin
  - optionally section admin if section follow-up is needed
- Why:
  Rejection usually needs corrective action.

**Section Notifications**

1. New staff added under your section

- Trigger:
  A `SECTION_STAFF` account is created under a section.
- Recipients:
  - the Section Admin of that section
- Why:
  Section Admin should know their team membership changed.

2. Staff moved to another section

- Trigger:
  A user’s section/division assignment changes.
- Recipients:
  - old Section Admin
  - new Section Admin
  - the affected user
- Why:
  Important for routing authority and visibility.

3. Staff removed or disabled in your section

- Trigger:
  A section staff account is disabled or removed from the section.
- Recipients:
  - the Section Admin of that section
- Why:
  Affects routing targets and section workload.

**System Notifications**

1. Password changed successfully

- Trigger:
  User changes password.
- Recipients:
  - the current user
- Why:
  Good security confirmation.

2. First login password-change requirement

- Trigger:
  A newly created user signs in using the generated/default password for the first time.
- Recipients:
  - the current user during login flow
- Why:
  This is not a regular bell notification. It is a forced account action and should remain part of the first-login password-change flow.

3. Important storage or upload issue

- Trigger:
  Upload failure, storage quota issue, or storage backend issue.
- Recipients:
  - affected user
  - optionally Super Admin if system-wide
- Why:
  Helps users understand what failed instead of guessing.

4. System maintenance or workflow rule change

- Trigger:
  Admin-defined system announcement or advisory.
- Recipients:
  - targeted roles or all users
- Why:
  Useful for controlled platform-wide communication.

**What Should Not Usually Create Notifications**

- page visits
- opening a document
- simple dashboard loads
- harmless metadata edits
- repeated duplicate confirmations for the same event

**Suggested Priority for Implementation**

Must Have First:

- account created under your section
- a routed file was shared with you
- route completed

Good Next Additions:

- section assignment changed
- document approved or rejected

Later / Optional:

- system maintenance notices
- storage/backend warnings
- confirmation notifications for successful low-risk actions

**Announcements**

Announcements are not the same as normal workflow notifications.

They should be treated as a separate feature with intentional authoring by Super Admin.

1. Announcement Purpose

Use announcements for:

- events
- reminders
- deadlines
- maintenance notices
- policy or workflow updates
- office advisories

2. Who Can Create Announcements

- Super Admin

This keeps broad system communication controlled and consistent.

3. Suggested Announcement Fields

- title
- message body
- audience
- priority
- start date
- end date
- optional link

4. Suggested Audience Options

- all users
- all section admins
- all section staff
- one specific section
- selected users

5. Suggested Priority Levels

- normal
- important
- urgent

6. Where Announcements Should Appear

- on login
- in the notification bell/feed if desired
- as a dashboard banner for important announcements

7. Important Behavior

- announcements should expire automatically after the configured end date
- announcements should not be confused with personal event-driven alerts
- announcements can be system-wide even when no file action triggered them

**Recommended Notification Payload**

Each notification should ideally contain:

- title
- short message
- category
- related object id
- target link
- created timestamp
- read/unread state

**Suggested Target Links**

- Account events:
  `/admin/users` or account settings page
- Routed file events:
  `/documents/view?id={document_id}`
- Dashboard summaries:
  `/dashboard` or `/admin/dashboard`
- Review events:
  related document view page

**Best Current Fit for This Project**

The best immediate fit for CDD-File-Tracking-System is a login-visible notification feed plus the existing bell/alerts experience.

That means:

- unread notifications should be visible immediately after login
- the bell should still show unread count
- notifications should deep-link to the relevant document or admin screen

**Important Current Exclusions**

These should not be treated as standard in-app notifications in the current workflow:

- fresh account welcome notifications
- disabled-user notifications that require login to read
- automatic route accept notifications
- automatic route decline notifications
- automatic review accept/decline notifications if no user-driven accept/decline step exists in the final workflow
- system-wide broadcast messages should be handled as announcements, not ordinary workflow notifications
